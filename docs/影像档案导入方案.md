# 把家庭影像档案导入布布时光机 · 实施方案

> 编写日期:2026-07-23
> 数据源:移动硬盘 `别动小爷的SSD/影像档案`(31,946 项影像,已完成整理、去重、人物确认、格式归一化)
> 目标:把布布的照片按"事件"导入时光机,形成可翻阅的时光轴

---

## 一、一句话结论

**技术上完全可行,而且不用改一行 iOS 代码。**
往 PocketBase 的 `entries` / `media` 集合写数据,App 的 `SyncEngine.pullRemote()` 会自动增量拉下来,
`localId` 唯一键天然保证重复导入不会产生脏数据。

**但不要全量导入。** 建议只导入 **134 条高密度事件**(覆盖 79% 的布布照片),
理由见第三节。

## 三、分组策略(为什么是 134 条而不是 2,712 条)

### 3.1 试过的几种分法

| 方式 | 产出条数 | 单张照片的条目 |
|---|---|---|
| 按天 | 351 | — |
| 按天 + 地点 | 438 | 132 条(30%) |
| 按间隔 3 小时切分 | 437 | 151 条(34%) |
| 3 小时切分 + 零星合并 | 392 | 109 条(28%) |
| **3 小时切分 + 只保留 ≥5 项的组** | **134** | **0** |

不管怎么切,**都有三成条目只有一张照片**。因为拍摄分布极端:少数几天上百张
(最大一组 259 张),大量日子只是随手拍一两张。

### 3.2 为什么不能让空壳条目进时光轴

看 `BubuTimeMachine/Models/Entry.swift`,一条 Entry 的字段是:

```
note              // 父母视角原文
firstPersonNote   // AI 改写的布布第一人称版本
moodRaw           // 心情标签
comments          // 家人合奏:多视角补充
inStorybook       // 收进成长绘本
```

**这个模型里的"一条记录"是一件事、一段叙述**,不是一堆照片。
自动生成 392 条没有 note、没有心情、没有家人评论的条目,
会把手写的那些真正用心的记录淹没掉——这个 App 的价值就没了。

### 3.3 采用的分组算法

```
1. 白名单 + 敏感排除(见第六节,缺一不可)     → 2,711 项
2. 按时间排序,同一天内相邻两张间隔 > 3 小时就切开(跨天必切)
3. 丢弃 < 5 项的碎片组                        → 134 组,覆盖 2,145 张(79%)
4. 每组:
   - happenedAt   = 组内最早一张的拍摄时间
   - locationName = 组内出现最多的地点(没有则留空)
   - title        = "YYYY年MM月DD日 " + (地点 或 时段词)
   - latitude/longitude = 组内第一个有 GPS 的坐标
   - note         = 留空,等你自己写
   - authorRole   = "档案导入"(便于日后区分/批量撤回)
5. 剩下 21% 的零散照片不丢,进素材库(见第六节)
```

**时段词**:清晨(<8)/上午(<12)/下午(<18)/晚上

### 3.4 生成效果实测(取最大的 6 条)

```
2025年05月10日 南头古城        259 项
2024年06月07日 上午            186 项
2024年08月23日 晚上            149 项
2026年05月17日 壹城中心         64 项

2024年11月09日 深圳万象天地      51 项(含 10 个视频)
```

地点名是从 GPS 反查出来的真实地名,不是编的。

## 四、两种部署路线(你二选一)

### 路线 A:把移动硬盘插到 Mac mini(推荐做一次性导入)

**优点**:一次插上,跑完导入就能拔,之后 App 完全不依赖这块盘。
**注意**:导入必须是**复制**而不是**引用路径**。
如果 PocketBase 里存的是 `/Volumes/别动小爷的SSD/...` 这样的路径,
**盘一拔布布的时光轴就全是裂图**——一个"拔了盘就坏"的时光轴比没有更糟。
PocketBase 的 `file` 字段本来就是上传后自建存储,照做即可,不要图省事改成路径引用。

**磁盘格式**:exFAT。macOS 原生支持,Mac mini 直接插即可。
(如果将来换 Linux 服务器需要 `exfat-fuse`,现代内核基本自带。)

### 路线 B:把档案数据拷到服务器挂载的 SSD

**只需要拷这些,不用拷 232 GB 全库**:

```
影像档案/99_影像检索与报告/影像数据库.sqlite      53 MB   ← 导入的唯一数据源
影像档案/99_影像检索与报告/缩略图/                3.9 GB  ← 全部缩略图(含非布布的,拷全省事)
影像档案/99_影像检索与报告/视频预览/              15 GB   ← H.264 副本
布布相关的照片原片                                11.6 GB ← 见下方筛选脚本
```

**只拷布布照片原片的清单生成方式**:

```bash
sqlite3 影像数据库.sqlite \
  "SELECT primary_final_path FROM assets WHERE daughter_status='已确认' AND kind!=1" \
  > /tmp/bubu_photos.txt
# 然后 rsync --files-from=/tmp/bubu_photos.txt 影像档案/ 目标目录/
```

**我的建议**:先走路线 A 做完首次导入(简单、不用管拷贝一致性),
确认效果满意后再决定要不要长期在服务器上放一份(那是"持续同步"才需要的,见第八节)。

## 五、字段映射(源 → PocketBase)

### entries 集合

| PocketBase 字段 | 来源 | 说明 |
|---|---|---|
| `localId` | 确定性 UUID(见下) | **幂等键**,重复导入不产生重复 |
| `happenedAt` | 组内最早 `captured_at` | 必填 |
| `title` | 日期 + 地点/时段 | 见 3.3 |
| `locationName` | `area`/`city` 众数 | 可空 |
| `latitude` / `longitude` | 组内首个有 GPS 的坐标 | 可空 |
| `authorRole` | 固定 `"档案导入"` | 必填;便于日后筛选和批量撤回 |
| `note` / `firstPersonNote` / `mood` | 留空 | 由你后续手写 |
| `isArchived` | `false` | |

**localId 必须是确定性的**,否则重跑导入会产生重复记录。建议:

```python
import uuid
NS = uuid.UUID('6f1b2c3d-0000-4000-8000-000000000001')  # 固定命名空间,自己定一个
entry_local_id = uuid.uuid5(NS, f"archive-entry:{组内最早照片的uuid}")
media_local_id = uuid.uuid5(NS, f"archive-media:{照片uuid}")
```

用"组内最早照片的 uuid"作种子,而不是组序号——这样即使将来重新分组,
已导入的条目也不会因为序号偏移而重复。

### media 集合

| PocketBase 字段 | 来源 | 说明 |
|---|---|---|
| `localId` | 确定性 UUID(同上) | |
| `entryLocalId` | 所属 entry 的 localId | 必填 |
| `mediaType` | `kind==1 ? "video" : "photo"` | |
| `file` | **照片**:原片<br>**视频**:`视频预览/<uuid前2位>/<uuid>.mp4`(H.264 副本) | 上限 500 MB |
| `thumbnail` | `缩略图/<uuid前2位>/<uuid>.jpg` | 上限 10 MB,现有平均 122 KB |
| `durationSeconds` | `duration` | 视频用 |
| `width` / `height` | 同名字段 | |
| `aiTags` | `auto_tags` 拆分成数组 | 已有视觉标签 |

**HEIC 照片的处理**:2,501 张照片里有 387 张是 HEIC。
iOS 原生认 HEIC,但如果将来想在网页端看,档案里已有对应的 2048px JPEG 预览
(`预览图/<uuid前2位>/<uuid>.jpg`)。建议 `file` 传原片(画质留给 18 岁的布布),
需要网页兼容时再用预览图。

## 六、安全红线(⚠️ 光有白名单不够,这里踩到过真雷)

档案库里有这些**绝对不能进一个会给家人看的成长 App** 的内容:

| 内容 | 数量 |
|---|---|
| **证件文档(含身份证正面和有效号码)** | **67 项** |
| 截图与网络图片 | 6,054 项 |
| 相似重复 | 1,882 项 |

### ⚠️ 实测发现:白名单里混着一张身份证

写这份文档时我跑了一遍自检,结果**不是 0,是 1**:

```
01_照片/01_女儿/2024/06/20240607_154515_城投·七里香榭_布布_身份证正面含号码_敏感证件_身份证_正面_FE6B6054.heic
document_type=身份证  document_side=正面  contains_valid_id_number=1  sensitive=1
```

**这是布布本人的身份证正面,含有效号码,而且它被正确地标成了"已确认是布布"**——
分类没错,它确实是布布的证件。但如果只按 `daughter_status='已确认'` 过滤,
**这张身份证就会直接进时光轴**。

所以规则要改成**白名单 + 敏感排除,两层都要**:

```sql
-- 导入用的最终筛选条件
SELECT a.* FROM assets a
LEFT JOIN asset_content_index i ON i.uuid = a.uuid
WHERE a.daughter_status = '已确认'
  AND COALESCE(i.document_type, '') = ''    -- 排除一切证件/文档
  AND COALESCE(i.sensitive, 0) = 0          -- 排除敏感标记
```

加上这两层后:**2,712 → 2,711 项**(剔除 1 张身份证),
分组结果不变(仍是 134 条 / 覆盖 79%)。

导入脚本必须自检**最终导入集**(不是自检白名单——白名单本来就会命中那张身份证):

```sql
-- 对最终筛选结果再查一遍,必须返回 0,否则中止导入
SELECT COUNT(*) FROM (
    SELECT a.uuid FROM assets a
    LEFT JOIN asset_content_index i ON i.uuid = a.uuid
    WHERE a.daughter_status = '已确认'
      AND COALESCE(i.document_type,'') = ''
      AND COALESCE(i.sensitive,0) = 0
) t
JOIN asset_content_index i2 ON i2.uuid = t.uuid
WHERE COALESCE(i2.document_type,'') != '' OR COALESCE(i2.sensitive,0) = 1;
```

同时打印一行"本次排除敏感项 N 条"(当前 N=1),让每次导入都能看见这个数字。
N 突然变大意味着档案库那边的识别结果变了,值得先看一眼再继续。

**教训**:"人物白名单"和"内容安全"是两个正交的维度。
一张照片可以既是"布布的",又是"绝对不能公开的"。别指望一个条件同时管住两件事。

另外:`note` 字段不要自动填 OCR 文本。档案里的 OCR 包含票据、聊天记录等内容,
自动灌进"父母视角原文"会很奇怪,而且可能带出隐私信息。

## 七、执行步骤

### 前置检查

```bash
# 1. PocketBase 在跑,且已应用全部 migrations
curl -s http://<mac-mini>:8090/api/health

# 2. 确认 media 集合存在且 file 上限是 500MB
#    见 server/pocketbase/migrations/1700000000_init_collections.js

# 3. 备份 PocketBase 数据(导入前必做,便于整体回滚)
cp -r server/pocketbase/pb_data server/pocketbase/pb_data.backup_$(date +%Y%m%d)
```

### 导入流程

```bash
# 1. 插盘(或挂载 SSD)后先看清单。安全自检内置,不通过会直接中止。
python3 scripts/import_archive.py \
    --archive "/Volumes/别动小爷的SSD/影像档案" --dry-run

# 2. 如果提示有视频超过 500MB(换了数据源时可能出现),先压一遍再回到上一步
python3 scripts/shrink_oversized_videos.py

# 3. 先导 3 条,去 iPhone 上确认照片、视频、缩略图、日期、地点都正常
python3 scripts/import_archive.py \
    --archive "/Volumes/别动小爷的SSD/影像档案" \
    --server http://<mac-mini>:8090 --user <你的账号> --limit 3

# 4. 确认没问题,跑完整 134 条(脚本幂等,前 3 条会自动跳过)
python3 scripts/import_archive.py \
    --archive "/Volumes/别动小爷的SSD/影像档案" \
    --server http://<mac-mini>:8090 --user <你的账号>

# 5. 打开 App 触发一次同步
```

密码走 `getpass` 交互输入,不会出现在命令行历史或脚本里。
脚本对每条记录先查 `localId` 是否已存在,存在就跳过——**中断后直接重跑即可续传**。

**建议先只导 3 条做验证**,在 iPhone 上确认照片、视频、缩略图、日期、地点都正常,
再跑完整的 134 条。

- **整体回滚**:停 PocketBase,恢复 `pb_data.backup_*`

## 八、待决定的事

### 8.1 一次性导入 vs 持续同步

- **一次性**(建议先这样):把 2024-2026 这两年灌进去打底,以后新照片手动记录。
  工程量:一个脚本,一天能跑完并验证。
- **持续同步**:以后拍的照片自动流进 App。工程量差一个量级——要处理增量、
  去重、冲突、以及"哪些新照片算布布的"(这依赖档案库的人物识别流程持续运行)。
  如果要做,建议先把一次性跑通、用一段时间,再决定。

### 8.2 剩下 21% 的零散照片怎么办

134 条覆盖了 79% 的布布照片,还有约 567 张散落在小于 5 项的组里。三个选项:

- **A. 先不导**(最简单,推荐):它们在档案库里随时能查到,不急
- **B. 导入但不建 Entry**:作为"素材库"存在,你翻到某天想写了再升格成记录
  ——这需要 App 侧加一个素材库视图(有 iOS 开发量)
- **C. 降低门槛到 ≥3 项**:变成 214 条、覆盖 89%,但会多出一批只有三张照片的薄条目

### 8.3 authorRole 填什么

`Entry.authorRole` 是必填,现有值是 "爸爸"/"妈妈"/"姥姥"。
我建议导入用 **"档案导入"** 而不是 "爸爸",理由:
- 一眼能看出哪些是自动导入的、哪些是手写的
- 批量撤回时有干净的筛选条件
- 你后来给某条补了文字,可以顺手把 authorRole 改成 "爸爸",等于"认领"

如果你希望时光轴上看起来统一,那就填 "爸爸",但回滚会麻烦一些。

## 九、这个方案没解决什么(如实说明)

- **人物识别只覆盖到 2024-05 之后**。档案里 `daughter_status='已确认'` 的最早一张是
  2024-05-22,更早的照片没有被确认为布布(可能是当时没做识别,也可能布布还没出生)。
  如果有更早的照片需要进时光轴,得先在档案库那边补人物确认。
- **674 项"相关待确认"没有纳入**。这些是疑似但没确认的,里面可能混有别的小孩,
  按白名单原则不导入。如果你想扩大覆盖,得先人工过一遍这 674 项。
- **note 全部为空**。自动生成的是"骨架",文字要你自己填。这是有意的设计,
  不是偷懒——见 3.2。

|---|---|---|
| 解决 | **历史存量**:2024-2026 已有的两年照片 | **日常增量**:今天刚拍的照片 |
| 人脸识别 | 用档案库已算好的结果(2,712 项已人工确认) | 端侧实时匹配 |
| 触发 | 一次性脚本,跑完即止 | App 内每天提示 |
| 落点 | 服务端 PocketBase → 同步下来 | 端侧直接建记录 |

**两者不冲突,而且顺序上应该先做本方案**:
先把两年历史灌进去,时光轴才有厚度;再做日常增量,才有"今天也记一笔"的动力。
反过来先做增量,时光轴前两年是空的,体验会很奇怪。

**一个要注意的口径问题**:`CLAUDE.md` 写明"人脸/图片分析一律端侧"。
本方案不违反这条——人脸识别是**早就在你自己的 Mac 上离线完成的**,
导入脚本只是读取已有结论,全程不联网、不外发。
但如果将来做增量同步,不要图省事把识别搬到服务端,那会破坏这条原则。
