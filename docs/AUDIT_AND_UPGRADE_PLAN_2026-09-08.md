# 布布时光机：全面审计、修复与下一步升级计划

> 本文为实施前的审计基线。已实施内容与实际发布证据以 [2.14.0 发布记录](RELEASE_2.14.0.md) 为准。

审计日期：2026-09-08。代码基线：`main / 8e19610`，开始时与 freshly fetched `origin/main` 一致，工作区干净。

**结论：先完成数据安全与服务端部署对齐，再增加功能。** 本轮已修复双端分页漏同步、iOS 保存失败仍推进游标、后端家庭隔离、原片搬盘后备份中断，并补齐真实 PocketBase 集成门禁。备份修复已在生产生效并完成恢复演练；业务权限迁移与客户端代码尚未发布，不能把本地测试通过当成线上已经修好。

## 1. 审计覆盖与限制

覆盖 iPhone/iPad、Apple Watch、HarmonyOS、PocketBase、FastAPI、照片摄取、软删除、时间胶囊、旧数据库迁移、备份恢复、运行中的服务与 CI。重点追踪近期 2.13.0 变更及数据/权限边界。

- iOS：完整 clean test、静态分析、真实旧版本数据库迁移回归、iPhone/iPad UI 自动测试与截图。
- HarmonyOS：全部合同/纯逻辑测试、DevEco 实际 ArkTS 编译与 HAP 打包。
- 后端：Python 3.9 与 3.11 测试；生产同版本 PocketBase 0.39.2 的隔离数据库集成测试。
- 线上：只读检查实际启动路径、数据库迁移记录、规则、健康与备份；修复并运行现有备份策略。
- 安全：鉴权/家庭隔离、上传令牌与暂存、URL 限制、胶囊降级、导出隐私、凭据模式扫描。未向第三方扫描服务上传源码或家庭数据。

没有进行手机覆盖安装、生产业务库迁移、GitHub push、真实家庭账号的跨端破坏性测试。Watch 验证为两种尺寸模拟器的启动与空态；未验证真实配对传输。HarmonyOS 编译成功不等于真机端到端验收。没有开展外部依赖漏洞库的全面匹配，不作“零漏洞”结论。

下一批不建议新增 AI 工坊、再铺平台或大面积拆分文件。现在最有价值的是让“这一刻保存了、家人看到了、几年后还恢复得出来”有完整证据。

### 保留的技术债

- SwiftData V1 仍引用活动模型类，`stages` 为空，不能做改名、删字段、改类型等破坏性模型变更。当前测试是旧库能打开的保障，不是真正版本迁移已完善。
- 双端单轮分页约十万条封顶，超过上限会报错并保留游标；接近此规模时改成逐页落盘和可恢复进度，避免一直全量重试。
- 同步本地查询仍有 `try? fetch` 路径，需在下一阶段通过存储故障注入逐一处理；本轮优先消除了已确认的保存失败静默路径。
- 媒体文件与数据库变更的跨资源原子性、并发跨设备写入的服务端版本比较，需要用真实端到端故障场景继续验证。
- 原片与镜像当前位于同一外接卷，镜像本身不具备“整盘损坏”隔离；已有 restic 双仓库本轮成功，但应单独确认本地第二仓库的物理介质与异地恢复能力。
